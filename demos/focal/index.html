FOCAL

Fundamentals-informed Optical Construction with Agentic Loops. Give it a lens specification (focal length, aperture, field, image quality) and it runs the textbook design procedure on its own: a starting form, numerical optimisation, a diagnosis, a structural change, and again. A ray tracer measures every candidate; a design is accepted only when it meets every requirement of the task.

  • 3roles in the loop: an Architect proposes starting systems, an Appraiser chooses the next change, a Reviewer writes the report. Each can be a language model or a rule-based policy.
  • 7acceptance checks per design, all numerical: focal length, F-number, total track, RMS spot at three field points, distortion, and manufacturability.
  • 6 / 7benchmark tasks met by the rule-based designer alone on a laptop CPU, in seconds each, confirmed by an independent verifier.
  • 0ways for the language model to overrule physics: the verifier's verdict is final, and the model's reasoning is only advisory.

How it works

the classical design loop, run by agents

  1. Start. The Architect reads the task and proposes two to four starting systems from textbook predesign (an achromat solve, a Cooke-triplet power solve, or an explicit prescription), each with a bending and a glass choice.
  2. Optimise. Damped least squares drives the aberration merit function down while holding focal length, F-number and manufacturing limits. The lens on screen moves at every accepted step.
  3. Verify. An exact ray tracer evaluates the candidate: polychromatic spot size at three field points, distortion at the specified angles, edge and centre thickness, vignetting.
  4. Diagnose and change. The Appraiser reads the aberration report and picks one structural move from a fixed catalogue: bend an element, change a glass, split a lens, move the stop, open an air gap, re-optimise. Then back to step 2, until the verifier accepts or the budget runs out.

What is new in FOCAL

  • A batched optimizer that keeps manufacturing constraints inside every step, so candidates stay buildable.
  • More starting forms (singlets, achromats, triplets, telephoto and Gauss types) and a trust-region refinement with an archive of promising branches.
  • An Explorer that reproduces published prescriptions and shows their checks and traced rays, so a known lens can be inspected the same way as a new one.
  • The live workbench: edit a task, press Start, follow the lens, replay any recorded run.

The design loop and acceptance rules follow Kingslake & Johnson, Lens Design Fundamentals. Results are reported as what the verifier measured, never as what a model claimed.

Try it

code and a local run

The code is in the lab's GitHub organisation on the focal branch. The repository is private while the work is under review, so sign in to GitHub with an account that belongs to the lab.

GitHub: wadduwagelab/lensharness Lab software

Python 3.12, CPU is enough. A language-model backend is optional: the rule-based policy runs offline, and Gemini, Claude or a local llama.cpp server can take the agent roles.

Local run

git clone --branch focal https://github.com/wadduwagelab/lensharness.git focal
cd focal && make venv
.venv/bin/focal experiments/task_cooke50.json --llm none --device cpu
make gui   # then open http://127.0.0.1:8765/design

The first command installs the harness and the pinned ray-trace backend into .venv. The second designs a Cooke triplet with the rule-based policy and writes the result under runs/.
